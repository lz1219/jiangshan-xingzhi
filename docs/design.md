## 1. 定位与非目标

**全项目定位**：让古籍读得懂，让解释查得到依据，让人物与作品回到历史时空中。兼具公共古籍阅读、文学历史阅读与专业考据三种用途，共享同一套文献、版本、证据与修订记录。

全项目长期目标与取舍统一维护在 [poem-data 项目总纲](../../poem-data/docs/project-charter.md)；内容职责、AI、审校与发布质量统一维护在 [编纂规范](../../poem-data/docs/editorial-policy.md)。两份文件是采纳的目标规范，不代表当前数据、界面和校验已经全部达标。

**本仓库职责**：提供历史空间、时间关系、人物行迹和文献入口。文献站承担原文阅读、译注赏析与研究复查；研究工作台保存来源、候选与核验过程。普通阅读、教学研读和专业研究按需展开，必要的摘录、待核与AI标识始终保留。

**名**：江山行止。行是位移，止是驻足；从时空线索进入文献，也能从文献回到人物与地点。

**与上游的关系**：本仓库是[江山时序](https://github.com/DeanChensj/jiangshan-map)的改造分支，不向上游提 PR；保留上游基座，本站内容由 poem-data JSON 生成并经扩展点接入。

**地图仓库的边界**：

- 保护上游地图渲染、疆域快照和数据文件；本站修订在 overlay 运行时生效。
- 数据编辑、后端和研究工作台放在 poem-data，本仓库保持纯静态。
- 前端保持零构建，不引入 npm 运行时依赖。
- 第三方资料按具体来源条件使用；古人原文、本站解释和AI推测区分。
- 按明确专题和核验范围扩展，长期馆藏不受最初74处地图引文限制。

## 2. 领域词汇表

术语以此为准，代码、文档、提交信息都用这套词。

| 词 | 含义 | 容易误解成 |
|---|---|---|
| **行 journey** | 一位人物的完整行迹，上游 `HISTORICAL_JOURNEYS` 的一条，共 7 条 | 不是「诗」；也不是我们的数据结构 |
| **止 stop** | 行迹中的一站：年份 + 坐标 + 古今地名 + 叙述 + 一句引文 | 不是「景点」；短途之游也占一站 |
| **引文 quote** | 站上的 `quoteZh`，形如 `苏轼《定风波》：「竹杖芒鞋…」` | 不是全文，是**摘句** |
| **作品 work** | 具有稳定标识的文献对象，关联正文版本、阅读解释与研究记录；字段按契约演进 | 与引文按书名关联，不是复制品 |
| **笺** | 点开引文后的阅读层：把摘句展开为作品 | 不是「赏析」，赏析只是其中一块 |
| **文体 genre** | `shi` 诗 · `ci` 词 · `fu` 赋 · `wen` 文 · `history` 史传 | 与「朝代」无关 |
| **摘录** | 文与史传只收被引用的段落，界面上必须标出 | 不是全本，也不是残缺 |
| **推测 inference** | 赏析中结合史事的推演，须给 `basis` | 与正文判断分开呈现，不得混写 |

## 3. 不可逆决策

**本节约束地图仓库实现。** 全项目定位与编纂要求见项目总纲和编纂规范；运行代码与数据仍用于判定实际已实现状态。

| # | 决定 | 理由 | 代价 |
|---|---|---|---|
| 1 | **以上游为基线改造，不向上游提 PR** | 上游 GPL-3.0 + 原生 JS + 单页；我们要改的正是交互与数据层，PR 形态只会变成「重写」 | 整个分支继承 GPL-3.0，不能闭源 |
| 2 | **只加不改：扩展点走 `__ATLAS_MIXINS`** | `app.js` 15k 行、无模块系统；改主逻辑的维护成本远超收益 | 受限于既有 DOM 与事件，样式要迁就 |
| 3 | **原文逐字据所选版本，保留初始基线** | 上游引文是起点，权威性与版本仍须核查；原文不可凭记忆重构 | 新版本在 poem-data 独立保存与说明，再生成地图内容 |
| 4 | **按专题收录，准确标明全文、摘录与残篇** | 阅读、翻译与引用必须知道文本边界 | 覆盖率按专题和范围统计，既有引文覆盖不回退 |
| 5 | **本站解释与古人评点分开，生成与审校可追踪** | AI起草和本站署名都不等于人工审校；推测须有据、单列 | 译注与赏析逐项记录来源和状态，目标规范分批落实 |
| 6 | **一切叙述必须有据，且写出处** | 读者凭这个项目读史；一句无据的因果就是造假。**不写史料未载的年龄、时长、因果、评价** | 写作变慢，每条都要能指到卷次；拿不准的部分只能不写 |
| 7 | **新增人物走 overlay，不改上游数据文件** | 上游 `lore_data.js` 是它的数据；我们另建 `atlas_overlay.js` 在运行时推入，才不会被 `git fetch upstream` 冲掉 | 多一层加载顺序依赖（必须在 `app.js` 之前） |

## 4. 里程碑与验收

阶段以全项目路线为准，当前顺序与任务状态只在 backlog 维护。

| 阶段 | 交付 | 验收口径 |
|---|---|---|
| 共同定位与规范（R-12） | 三类用途、馆藏边界、编纂与AI规则 | 三类读者都能理解所获内容、核验深度和能力边界 |
| 通用内容与阅读模型（R-13） | 独立译文、定位注释、分节赏析、生成和审校记录 | 先核来源，贯通发布JSON、数据库往返及两站；三类文体样板验证完整流程 |
| 来源与专题建设（R-11） | 原典版本、事实证据与缺口清单 | 按明确对象和核查范围推进，不把机器命中算成人工核定 |
| 文体与研究深化（R-4、R-6） | 新文体、检索与后续专业功能 | 保留共同知识体系、渐进阅读、旧引用与上游扩展约束 |

现有摘句阅读器、作品检索、生成链和独立考据笺是基础能力；不代表通用译注模型、全库人工审校、多版本对读等长期目标已完成。既有引文覆盖率仍须保持，旧里程碑的完成记录见 backlog 和 progress。

## 8. 与文献站（poem-data）的互链

两个站点分工：

| 站点 | 回答的问题 | 数据 |
|---|---|---|
| **江山行止**（本仓库） | **在哪** | 疆域、行迹、站点、地图 |
| **文献**（poem-data） | **怎么读** | 作品注疏、人物仕历、66,968 首诗、1,301 卷原典 |

**职责互补**：地图呈现时空关系，文献站提供完整译注和研究深度；用对象深链互通，保持相同来源、状态与修订关系。

### 链接地址可配置

`js/atlas_links.js` 是唯一配置点：

```js
window.ATLAS_CORPUS_BASE   // 外层页面可预设；默认按环境推断
```

- 本地：`http://127.0.0.1:5322/`
- 线上：`https://lz1219.github.io/poem-data/`

两个站点换部署地时，只改这一处（或在页面里预设变量），**不需要动渲染代码**。

### 三处入口

| 位置 | 链接 |
|---|---|
| 阅读器底部 | 在文献站读全篇 ↗ |
| 人物面板导语下 | 在文献站查此人 ↗ |
| 文献站侧 | 行迹站点「地图 ↗」、人物「在地图上看 ↗」、作品徽标行「地图 ↗」 |

### 一个坑

`ATLAS_WORKS` 的条目里**没有 key 字段**（key 是对象的键名）。互链需要 key，
所以 `findPoem()` 命中时会把键名补到 `poem.__key` 上，不污染原数据。

### 生成物（勿手改）

`js/atlas_works.js`、`js/atlas_overlay.js`、`js/atlas_journeys.js` 现在**由 poem-data 生成**：

```bash
# 在 poem-data 仓库里
node scripts/emit-atlas.mjs --target ../jiangshan-xingzhi
```

- 内容源头：`poem-data/data/*.json`
- 上游已有行迹通过 overlay 在运行时修订同年同地站点，不修改上游文件；同键多站拒绝歧义覆盖。未知年份放入独立补充区，不进入上游排序和跳年。
- poem-data 的提交闸门会跑 `--check`，生成物落后于数据时拒绝提交

**要改内容，去 poem-data 改，不要改这三个文件。**
